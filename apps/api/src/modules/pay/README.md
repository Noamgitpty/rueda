# PAY — Payments abstraction (`apps/api/src/modules/pay`)

**PAY — Payments abstraction** : adaptateurs PSP, opérations de paiement, commandes monétaires, webhooks, remboursements. Dépendances autorisées : CFG, CTR, AUD (socle implicite : CFG, AUD, BUS ; source : 17 §2.2 (CTR : mandat)).

## Responsabilité

D'après 17 §2.2 et §2.8 : adaptateurs PSP de place de marché, compte marchand de Kmino par pays, sous-marchands hôtes, matrice de capacités, registre des opérations avec montants par jambe, boîte d'envoi des commandes monétaires, webhooks entrants, puis instruments, consentements MIT, chargebacks, remboursements (SM-8) et caution. Aucun code métier ne connaît un PSP. PAY ne calcule aucune jambe : elles viennent du règlement (STL, 08 E7).

État du code :

- **livré** : port `PaymentProvider` avec contrôles de jambes, capacités fail-closed, erreurs normalisées, clés d'idempotence, envoi des commandes monétaires, réception et traitement des webhooks, détecteur de PAN (UUID et empreintes `hex(sha256)` de 64 minuscules écartés : ADR-155, migration 0131), adaptateurs PostgreSQL et garde de démarrage (US-019, ADR-059) ; méthodes de place de marché et sous-marchands (US-061, ADR-066) ;
- **FAKE seulement** : le registre des PSP de production est vide jusqu'au lot C (US-601) ; un FAKE n'est jamais actif en production (C19) ;
- **livré par US-223 (223a, ADR-139)** : preuve par webhook seulement (montant et devise du webhook vérifiés en base, `MISMATCH` ; horodatage signé absent hors fenêtre ; aucune lecture ni réponse d'un compte LIVE ne prouve ; `UNPROVEN` et `MISMATCH` traités par `WebhookProcessor` : `FAILED` à motif dédié et alerte) ; lecture avant tout envoi sans `SUPPORTS_IDEMPOTENCY_HEADER` (N-108, `MoneyCommandSender`) ; tâches `webhook_ingest` et `booking_conversion` du travailleur (`worker-tasks.ts`) ;
- **pas encore** : routes HTTP du paiement (US-223 partie 223b), mode `REQUEST` (223c), instruments, MIT, remboursements, caution, chargebacks, dettes.

Détail fichier par fichier, FAKE et mode hostile : [`internal/README.md`](internal/README.md).

## Caution « comme Turo » (US-225 ; 08 BR-PAY-06 ; ADR-108, ADR-164)

**Aucune caution par défaut.** Une caution n'existe que si un déclencheur paramétré par pays est vrai (`deposit_always_required`, `deposit_trigger_classes` = {LUXE}, âge sur `deposit_young_driver_classes` = vide au PA et au PY, signal de risque si `risk_control_deployed`) : graine `0142`, valeurs PROPOSÉES. Au checkout, avant le paiement, `decideDepositGate` rend `NOT_REQUIRED` (aucun rail évalué), `REQUIRED` avec le rail choisi par configuration, ou un refus (`PARAM_MISSING` si `deposit_amount` manque, `DEPOSIT_RAIL_UNAVAILABLE` avec les jours possibles). Le rail « débit puis remboursement » reste fermé tant que `funds_holding_enabled[pays]` = `false` (aucun fonds de tiers détenu) ; une capacité PSP inconnue vaut « non ». `planDepositDecision` et `DepositRailExecutor` exécutent la décision sur le port (FAKE seulement) avec le montant explicite de chaque commande. **Non branché** au checkout ni à un travailleur dans cette story : `deposit_hold`, l'écriture au checkout, les minuteries et l'écran S05 sont à US-701 / US-702 (voir `docs/team/handoffs/US-225.md`).

**Avant le checkout** (US-701c, T70 c ; ADR-173) : `preCheckoutDeposit` (pur : `evaluateDepositTriggers(…, 'PRE_CHECKOUT')` puis `depositAmountFor`) et `PreCheckoutDepositReader` (`internal/deposit-notice.ts`, paramètres du pays par `PgDepositRailConfigReader`, sans compte marchand) rendent `GENERIC`, `REQUIRED` (montant) ou `UNAVAILABLE` (déclencheur vrai, montant absent : le checkout refusera, `PARAM_MISSING`) pour la fiche et les cartes de CAT (port `ListingDepositPolicy`, câblé par `main.ts`).

### Caution figée au checkout, vue du voyageur, minuterie (US-701 ; ADR-169)

- `DepositCheckoutGate` (`internal/deposit-checkout.ts`) : `view` (S05 : décision figée, ou évaluée **sans écriture** tant qu'un paiement est possible) et `enforce` (avant T1 : refus ⇒ aucune ligne ; sinon décision figée une fois par `core.payment_cmd_record_deposit_decision`, `EXISTING` ensuite). `evaluateDepositCheckout` (pur) rend la décision, la ligne à figer (mécanisme, déclencheurs [C2], instantané des paramètres [C2], montant, `H_requise`, `V`, échéancier de `planDepositSchedule`) et la vue du voyageur `DepositGuestView` (statut, montant, devise, `HOLD` / `CHARGE`, libération ; ou refus et jours possibles), jamais un champ [C2]. Âge des conducteurs et signal de risque non lus ici : inconnus, donc fail-closed (suite S-10).
- `PgDepositCheckoutStore` (`internal/pg-deposit-checkout.ts`) sous `app_api` : `core.payment_deposit_checkout`, `core.payment_cmd_record_deposit_decision` (0146).
- `DepositReauthTimer` / `registerDepositTimers` (`internal/deposit-timer.ts`) : tâche `deposit_timer` (60 s, nom `payment_command`) ; file `core.payment_deposit_reauth_due`, ré-autorisation par le port hors transaction, transition `core.payment_cmd_deposit_transition` (rang attendu) ; refusée ⇒ décision avancée à `expiration − deposit_safety_h`, alerte `DEPOSIT_REAUTH_FAILED`, aucun débit ; en cours ou inconnue ⇒ aucun changement, même clé au passage suivant. Aucun connecteur en production avant le lot C.
- `DepositRailExecutor.reauthorize` : `SUCCEEDED` seul ⇒ `REAUTHORIZED` ; `PENDING` / `SUBMITTED` / `UNKNOWN` / `UNKNOWN_OUTCOME` ⇒ `REAUTH_PENDING` (`needsLookup`).
- US-222d2 (F-L2-LB-03, ADR-177) : sans `SUPPORTS_IDEMPOTENCY_HEADER` validé (inconnue = non), chaque ordre de la caution (capture, VOID, remboursement, MIT, ré-autorisation) est précédé de `getOperation` par notre clé (lecture d'abord, comme `MoneyCommandSender`) : une opération trouvée est reprise telle quelle, rien n'est renvoyé ; sans `SUPPORTS_LOOKUP_BY_MERCHANT_REF` non plus, rien n'est envoyé (`UNSUPPORTED_CAPABILITY`). Preuve : `testing/redteam/l2-lb-mit.test.ts` (PA USD, PY PYG).
- Clés d'idempotence (S-6, 08 E4) : `{trip}:{segment}:v0-DEPOSIT-{caution}:{opération}:{moyen}:i{n}:a{m}` (`depositOperationKey`) ; remboursement du rail (b) = `offSettlementRefundKey` d'origine `DEPOSIT`.

### Décision de la caution à l'heure de décision (US-702 ; ADR-172)

- **Échéancier recalculé par la base** : `core.payment_cmd_record_deposit_decision` (0150) ignore `provider`, `authAt`, `releaseAt`, `decisionAt`, `reauthDueAt` de la décision envoyée et les recalcule (compte marchand du pays, durées `auth_lead_h`, `release_delay_h`, `deposit_safety_h`, `deposit_reauth_lead_h` lues en base) ; `V` reste l'instantané, borné. Le site lit toujours la libération figée en base.
- `DepositDecisionTimer` / `PgDepositDecisionStore` (`internal/deposit-decision.ts`), dans la tâche `deposit_timer` après les ré-autorisations : file `core.payment_deposit_decision_due` (décision échue ou autorisation expirée ; rien ne la suspend), plan `planDepositDecision`, exécution `DepositRailExecutor.execute` hors transaction, transition finale `core.payment_cmd_deposit_decide` (rang attendu, Σ capturé + libéré = montant) qui écrit `deposit.decision.executed`. Autorisation expirée ⇒ `EXPIRED` sans appel ; issue inconnue ⇒ même clé au passage suivant ; VOID refusé ⇒ laissée expirer, `DEPOSIT_DECISION_FAILED` ; MIT impossible ⇒ libérée quand même, `DEPOSIT_FEES_UNCOLLECTED`. US-702b (0153) : la file et la garde suivent la décision EFFECTIVE (retour réel, `(checkout_at ?? scheduled_end) + 72 h`, un retour tardif ne prolonge jamais l'autorisation) ; PSP injoignable au VOID (`PROVIDER_UNAVAILABLE`) ⇒ ce n'est pas un refus : rien d'écrit, nouvel essai ; `DEPOSIT_DECISION_FAILED` d'un échec non final envoyée une fois par caution et par cause (mémoire bornée du processus, `DEPOSIT_DECISION_ALERT_MEMORY`).
- `DepositFeeSource` : frais annexes et carte du consentement MIT ; en production `NO_DEPOSIT_FEES` (aucun registre des frais annexes encore : caution libérée en entier, frais ensuite par MIT, PROPOSÉ).

## Carte enregistrée, consentement MIT et débits post-trip (US-703 ; 16 PAY-015 / PAY-037 ; ADR-189)

- **Consentement au checkout** (S05) : `CheckoutPaymentService` d'AVL exige `mitConsent: true` (case séparée, non pré-cochée, `web.s05.mitConsent`) et la langue du texte ; sinon `422 MIT_CONSENT_REQUIRED` avant toute écriture ; puis `PgMitConsentStore.accept` (`core.payment_cmd_accept_mit_consent`, une fois par hold), juste avant T1.
- **Rappel à la remise** (S09) : `HandoverService` de TRP, à la validation du départ par le voyageur (langue du rappel affiché), appelle `PgMitConsentStore.acknowledgeReminder` (`core.payment_cmd_ack_mit_reminder`) ; un échec n'empêche jamais la remise.
- **Débits** : `core.payment_cmd_notify_post_trip_charge` (décision amont, montant explicite de chaque jambe) ; tâche `mit_charge_scheduler` (`MitChargeScheduler`, 60 s, travailleur `payment_command`) : la base planifie chaque tentative (`core.payment_cmd_plan_mit_attempt` : consentement, rappel, carte, règle du réseau en données `core.payment_mit_network_rule`, préavis, accord, délai, `SUPPORTS_MIT` inconnue = non, J0 / J+3 / J+7, une instance i1, `attempt_no` + 1 après un refus reçu), puis l'ordre stocké est envoyé par `MoneyCommandSender` (`chargeMIT`, lecture d'abord) et l'issue reportée (`core.payment_cmd_settle_mit_attempt`) ; refus définitif ou dernière tentative ⇒ dette et `UNPAID_BALANCE`. Aucun `MIT_CHARGE` ni `DEBT_COLLECTION` hors d'une tentative ou d'un encaissement planifié (déclencheur `payment_operation_mit_guard`). Aucun connecteur en production avant le lot C : rien n'est planifié ni envoyé.
- **Encaissements partiels d'une dette** : `core.payment_cmd_plan_debt_collection` (jambes de 08 E7 règle 4 révisée, `core.payment_partial_collection_legs`, la même règle que `partialCollectionLegs` de `@rueda/money`) et `core.payment_cmd_settle_debt_collection` (cumul sur preuve, restriction levée au solde). Rail du paiement d'une dette : lot C.
- La caution n'est jamais capturée pour un débit post-trip (aucun `DEPOSIT_*` dans ce chemin).

## Événements

Émis par une fonction de la base appelée par PAY : `deposit.decision.executed` (0150, US-702 ; `deposit_id`, `trip_id`, `status`, `captured_minor`, `released_minor`, `currency`, `decided_at` ; 0153, US-702b : `notice` et `auth_expiry_at`), consommé par NTF (avis au voyageur). Aucun autre événement de domaine n'est émis ni consommé par le code de PAY aujourd'hui. Chaque statut reçu est écrit dans `core.payment_payment_operation_event` (pas un événement d'outbox). La commande `CANCEL_ORDER` est écrite dans `core.payment_payment_command` par les commandes du hold (AVL, migration 0040), pas par un événement.

Cible (17 §2.2, §4.5) :

- émis : `payment.received`, `payment.operation.status_changed`, `payment.chargeback.opened` / `.closed`, `refund.instance.status_changed`, `deposit.decision.executed` ;
- consommés : `booking.hold.*` et `booking.hold.release_requested` / `.superseded` (annulation d'ordre), `booking.request.*`, `booking.hold.compensation_required`, `settlement.legs.*`, `settlement.computed`, `settlement.superseded`, `insurer.bordereau.issued`, `risk.review.*`, `invoice.status_changed`, `evidence.bundle.generated`, `payment.chargeback.opened`.

## Ports

- `PaymentProvider` (`internal/port.ts`, 17 §2.8) : toute méthode qui déplace des fonds reçoit des `LegAmounts` (`MONEY_MOVING_METHODS`) ; méthodes de place de marché idempotentes (`MARKETPLACE_WRITE_METHODS`).
- `WebhookVerifier` : vérification de signature par fournisseur, utilisée par `WebhookIngestService`.
- Magasins (`internal/stores.ts`) : `OperationStatusStore`, `WebhookInboxStore`, `WebhookWorkStore`, adaptateurs PostgreSQL `PgOperationRecorder`, `PgWebhookInboxStore`, `PgWebhookWorkStore`. US-224 (ADR-145) : `PgOperationRecorder.record` appelle la commande à 15 arguments ; un ordre REFUND / LEG_REALLOCATION / LEG_RELEASE d'un trip porte `settlement` (identifiant et version en tête du règlement), sinon la base le refuse ; un webhook de ces ordres sans montant ne les prouve pas (`UNPROVEN`). US-224b (ADR-147) : `PgRefundPlanner` planifie un remboursement de règlement (`plan` : instance SM-8, avance de Kmino attendue si la part HOST est déjà versée, ordre PENDING) et autorise son envoi (`submit` : `SUBMITTED`, `DUPLICATE`, `SUPERSEDED` ou `BLOCKED` avec son motif, tant qu'une avance n'a pas de décision FINANCE à deux personnes) ; l'appel au PSP ne suit que `SUBMITTED`. US-224c (ADR-150) : `PgRefundOrders` (`due` : file de l'ordonnanceur ; `orderForSend` : ordre stocké relu sous les verrous du trip et de l'ordre, gardés pendant l'appel au PSP, refus `NOT_SUBMITTED`, `FINAL`, `SUPERSEDED_UNSENT`, `NO_TARGET` ; `markAlerted` ; `applyLegMovement`) ; `PaymentConnectorRegistry` et `PRODUCTION_PAYMENT_CONNECTORS` (aucun connecteur avant le lot C) ; `REFUND_INSTANCE_STATUSES` (types resserrés de `PgRefundPlanner`, N-227). US-224f (ADR-166) : `PgRefundOrders.awaitChoice` (instance `FAILED` après un rejet confirmé ⇒ `PENDING_CUSTOMER_CHOICE`, `attempt_no` + 1 ; `DUPLICATE`, `SUPERSEDED`) ; la base refuse un rail natif sur un moyen autre qu'une carte et tout remboursement d'un moyen au-delà de ce qu'il a payé. US-224 (durcissement argent n° 2, 0152, ADR-166 n° 9, N-367) : `core.payment_cmd_record_operation` refuse tout encaissement par crédit (`CREDIT_REDEMPTION`, ou encaissement d'un moyen `CREDIT_CASH` / `CREDIT_PROMO`) tant que les crédits n'existent pas : `payment_operation_credit_unavailable` ⇒ `PAYMENT_METHOD_UNAVAILABLE` ; `markAlerted` prend le verrou du trip avant l'instance (N-364).
- FAKE : `FakePsp` de `@rueda/fake-adapters/psp`, traduit vers le port par `testing/fake-payment-provider.ts` ; `testing/` n'est exporté par aucun index et reste hors de la compilation de production.

API publique (`index.ts`, liste complète dans le fichier) : `PayModule`, `PayWebhookModule`, `postgresPayAdapters`, `PRODUCTION_PROVIDERS` ; types et constantes du port ; jambes (`LEGS`, `assertMovingLegs`, `legSum`…) ; erreurs (`PaymentError`, `PAYMENT_ERROR_CODES`) ; capacités (`CapabilitySet`, `CAPABILITIES`) ; idempotence (`settlementOperationKey`, `holdAttemptKey`…) ; `MoneyCommandSender` ; webhooks (`WebhookIngestService`, `WebhookProcessor`) ; PAN (`containsPan`, `maskPan`) ; démarrage (`assertPaymentStartup`, `checkPaymentStartup`).
