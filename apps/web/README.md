# @rueda/web

Application Next.js (App Router), mobile-first et installable (PWA, ADR-039, ADR-072) : voyageur et espace hôte, même application, en es / en / fr / pt.

## Coquille et PWA (US-048)

| Élément        | Où                                                                              | Rôle                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Marque         | `brand-source.ts` (`getRequestBrand`)                                           | nom, thème, logo : `GET /brand` (US-034) si `WEB_BRAND_API_URL`, revalidé et recompilé ici ; sinon thème embarqué (fail-closed)       |

## Textes éditables et en-têtes de sécurité (US-121, ADR-095)

- **Blocs de contenu** (`content-source.ts`, `app/rich-text.tsx`) : avec `WEB_BRAND_API_URL`, l'accueil lit `GET /brand/content` (langue de la page ; pays = région de la locale, `es-PA` ⇒ PA) et remplace chaque texte du catalogue visé par le registre `EDITABLE_BLOCKS` de `@rueda/i18n`. L'arbre reçu est revalidé (`isRichDoc`) puis rendu en éléments React, jamais en HTML (aucun `dangerouslySetInnerHTML` pour les blocs ; le seul usage du site est `theme.tsx`, qui injecte la feuille compilée depuis des jetons validés). La description de la page (`layout.tsx`) suit le bloc de l'accroche. Un bloc absent dans la langue de la page, un arbre invalide, une API lente ou en erreur : le texte du catalogue livré, dans la langue de la page (jamais un bloc vide, jamais deux langues). Cache 30 s, délai 1,5 s.
- **En-têtes** (`security-headers.ts`, toutes les routes par `next.config.ts`) : CSP `default-src 'self'` (ni objet, ni `<base>`, formulaires vers le site, jamais en cadre ; `'unsafe-inline'` pour l'amorçage de Next et le thème, faute de nonce), `nosniff`, `X-Frame-Options: DENY`, caméra et position limitées au site, micro refusé.

Changer le nom, les couleurs, le logo ou les icônes : publier une version de marque (US-034, `apps/api/src/modules/cfg/internal/brand/README.md`) ou changer de palette (`packages/design-tokens/README.md`). Aucun déploiement du site n'est nécessaire avec `WEB_BRAND_API_URL`.

Contrôle à 360 px (défilement horizontal, cibles ≥ 44 px, écran hors ligne par le vrai service worker) et captures : serveur démarré (`pnpm --filter @rueda/web build` puis `start`), puis `node apps/web/scripts/shell-check.mjs http://localhost:3000`. Captures dans `docs/design/US-048/`. Outil local ; le harnais e2e Playwright de la CI reste à créer.

## Parcours e2e Playwright (US-041)

`e2e/` : parcours d'un utilisateur réel contre le **build de production** (`next start`, démarré par Playwright), dans le Google Chrome installé (`channel: 'chrome'`, aucun navigateur téléchargé). Décision : ADR-074.

- **Viewports** (projets de `playwright.config.ts`) : `mobile-360` et `mobile-390` (téléphone tactile), `tablette` (768 px) pour `shell.spec.ts` ; `pwa` (390 px, service workers autorisés) pour `pwa.spec.ts`.
- **Coquille** (`shell.spec.ts`) : accueil et écran hors ligne en es, en, fr et pt, clair et sombre ; aucun défilement horizontal ; aucune cible tactile sous 44 px (règles de `scripts/shell-check.mjs`) ; luminance du fond selon le mode ; changement de langue mémorisé ; bandeau hors ligne puis retour en ligne annoncés.
- **PWA** (`pwa.spec.ts`) : manifeste complet dans les quatre langues (icônes PNG aux tailles déclarées, une `maskable`) ; service worker réel : page jamais visitée, réseau coupé, écran hors ligne dans la langue, reprise au retour du réseau ; **application installée** : fenêtre d'application de Chrome (`--app`, `display-mode: standalone`, `e2e/app-window.ts`) sur un profil persistant, verdict d'installabilité de Chrome vide, parcours hors ligne dans cette fenêtre.
- **Accessibilité et régression visuelle** (US-044, ADR-112) : `screens.spec.ts` balaie chaque écran du site (liste `SCREENS`, état d'arrivée) et `console.spec.ts` chaque état de la console interne (`apps/backoffice`, démarrée par Playwright sans API, `/api/**` intercepté ; projets `console-360` et `console-390`) : axe-core sur la page entière (`e2e/axe.ts`, partagé par tous les parcours), quatre langues, clair et sombre, mobile d'abord, captures `toHaveScreenshot` comparées aux références de `e2e/__screenshots__/linux/`. Un nouvel écran s'ajoute à `SCREENS`. Procédure d'approbation : `docs/qa/REGRESSION_VISUELLE.md`. La vitrine `/ui` est ouverte pour les e2e seulement (`WEB_UI_CATALOG_ENABLED=true` du serveur de test).
- **Aucun parcours orphelin** : chaque `e2e/**/*.spec.ts` doit figurer dans le `testMatch` d'au moins un projet de `playwright.config.ts`, sinon il ne tourne jamais en CI. Le garde-fou `e2e-projects.test.ts` (dans `test:unit`, job `qualite`) échoue sinon ; il refuse aussi un motif qu'il ne sait pas évaluer (glob en chaîne). Un nouveau parcours s'ajoute donc à la config dans la même PR. Parcours de l'hôte lancés à 360 et 390 px : `host-listings` (US-115), `host-verification` (US-123), `host-calendar` (US-119, A06), `host-trips` (US-219, A02 / A05).
- **Déterminisme** : aucune relance, mouvement réduit, fuseau UTC, `Date` figée (`FROZEN_AT`) ; toute requête vers un autre hôte que le serveur testé fait échouer le test. Valeurs attendues : 10b §4.3 (`e2e/oracle.ts`), jamais le code testé.

```bash
pnpm turbo run build --filter=@rueda/web
pnpm --filter @rueda/web test:e2e                      # tous les projets
pnpm --filter @rueda/web exec playwright test --project=mobile-360
```

En CI : job `e2e-web` de `ci.yml` (docs/ops/CI.md). Variables : `RUEDA_E2E_PORT` (défaut 3100), `RUEDA_E2E_CONSOLE_PORT` (défaut 3102), `RUEDA_E2E_CHROME`. Build préalable : `pnpm turbo run build --filter=@rueda/web --filter=@rueda/backoffice`. `scripts/shell-check.mjs` reste l'outil local des captures de revue design.

## Inscription, connexion et consentements (US-102)

Écrans S15 dans la coquille, maquette US-033 : `/signup` (nom et prénom comme sur le permis, e-mail, mot de passe, case CGU + confidentialité obligatoire, opt-in des communications ; jamais pré-cochées), `/signup/sent` (écran identique que l'email soit libre ou pris), `/legal/{TOS_GUEST|PRIVACY|MARKETING}` (version, mention BROUILLON), `/login`, `/terms/update` (réacceptation après une version majeure), `/login/done`, `/verify-email`. Formulaires par actions serveur : ils fonctionnent sans JavaScript. Le navigateur ne parle qu'au site ; le **serveur** appelle l'API par `WEB_API_URL` (`account/api-client.ts`) et repose le cookie `__Host-session` (ADR-091). Sans `WEB_API_URL` ou sans documents : aucun formulaire, message « documents indisponibles » (fail-closed).

e2e : `e2e/signup.spec.ts` (projets `mobile-360` et `mobile-390`, quatre langues, axe-core WCAG 2.2 A / AA sur `main`) contre le double `e2e/stub-api.mjs`, démarré par Playwright (`RUEDA_E2E_API_PORT`, défaut 3199).

## Compte de versement de l'hôte — US-707

`app/(app)/host/payout-account/` (lien depuis la tâche « compte de versement » d'A07) : compte bancaire ou portefeuille **au nom de l'hôte** (16 PYO-001), lu et écrit par `GET` / `POST /host/accounts/{orgId}/payout-account` (côté serveur seulement). Type de compte choisi par liens `?kind=` (sans JavaScript) ; établissement en liste ou en code selon la configuration du pays (`rails`, jamais une constante) ; numéro fiscal absent ⇒ lien vers le profil fiscal d'A07, aucun formulaire ; pays sans rail ⇒ dit honnêtement. Ni le numéro de compte ni le numéro fiscal ne sont réaffichés, mis dans une URL ou renvoyés à l'écran après un refus ; un co-hôte reçoit `common.payoutAccount.manageForbidden`. ## Interfaces d'appareil (`device/`)

Le comptoir n'accède à l'appareil que par trois interfaces (17 §6.2, ADR-005). Point d'entrée unique : `device/index.ts`.

| Interface       | Rôle                                                                         | Adaptateur web                                     |
| --------------- | ---------------------------------------------------------------------------- | -------------------------------------------------- |
| `CameraCapture` | capture **en direct** dans la page, jamais d'import de galerie               | `camera-capture.web.ts` (`getUserMedia` + canevas) |
| `OfflineQueue`  | file locale chiffrée (AES-GCM, clé non exportable), empreinte, reprise       | `offline-queue.idb.ts` (IndexedDB)                 |
| `DeviceGeo`     | position + précision, chaque issue est un résultat typé (jamais d'exception) | `device-geo.ts` (`navigator.geolocation`)          |

La logique (dimensions et poids des photos, ordre de la file, empreinte SHA-256, chiffrement, vidage, erreurs de position) est testée en unitaire (`pnpm test:unit`). Un repli natif (enveloppe Capacitor, terminal fourni) ne remplacerait que les adaptateurs.

Politique de photo (TRP-002) : grand côté ≤ 1 600 px, ≤ 500 ko (500 000 octets), JPEG. Valeurs PROPOSÉ, codées dans `DEFAULT_PHOTO_POLICY` en attendant un paramètre de 17 §7.2.

## Thème (US-030)

La page reçoit dans `<head>` les variables CSS du thème actif (`theme.tsx`, paquet `@rueda/design-tokens`). Les composants n'écrivent que `var(--…)` : `pnpm lint` refuse toute couleur, police, taille, espacement, rayon, ombre ou durée en dur. Changer de palette : voir `packages/design-tokens/README.md`, « Changer de palette en 1 étape ».

## Bibliothèque de composants (US-032)

Les écrans utilisent les composants de `@rueda/ui` (voir `packages/ui/README.md`). La vitrine vivante est servie sur **`/ui`** (`?lang=`, `?theme=auto|light|dark`, `?width=mobile|full`) : ouverte en `next dev`, sinon seulement avec `WEB_UI_CATALOG_ENABLED=true`.

## Prototype des écrans clés (US-033)

Prototype cliquable des parcours voyageur, hôte et plateforme sur **`/proto`** (index) et `/proto/<écran>` (`s01` … `s09`, `s09c`, `s14`, `s15`, `s17` ; `a01` … `a13` ; `o01`), dans le seul dossier `app/proto/` (ADR-073). Paramètres : `?lang=`, `?state=` (vide, chargement, erreur…), `?theme=auto|light|dark`, `?market=` (marché fictif de `app/proto/data/scenario.json`), `?capture=1`. Données fictives, aucun appel d'API, paiement simulé. Textes : `app/proto/copy/` (format de `@rueda/i18n`, quatre langues). Captures et approbations : `docs/design/US-033/`. Ouvert en `next dev`, sinon seulement avec `WEB_PROTOTYPE_ENABLED=true`.

| Variable                  | Défaut  | Effet                                                                                                                                                                                                                                                   |
| ------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WEB_LAB_PWA_IOS_ENABLED` | absente | `true` (exactement) ouvre le laboratoire US-026. Toute autre valeur, ou l'absence : la page, le manifeste, le service worker et les icônes répondent **404**. Lue à chaque requête côté serveur (pas de `NEXT_PUBLIC_`), donc rien n'est figé au build. |
