## Défauts trouvés (rapportés à l'orchestrateur ; tests `it.fails`)

- **D1 — la capture prouvée d'un hold de checkout n'est jamais portée sur les soldes par jambe du trip réservé.** `core.booking_convert_payment` (0126) crée le trip sans rattacher l'opération de capture (`payment_operation.trip_id` reste NULL) ; `core.settlement_cmd_apply_leg_movement` (dernière version 0123) refuse une opération sans `trip_id` (`leg_movement_unsupported`) ; aucun code de production n'appelle d'ailleurs ce report pour une capture (seul `RefundScheduler` l'appelle, pour un remboursement ; le consommateur `payment_command` n'est pas déclaré, `worker-tasks.ts`). Preuve : run 44379275642, job « base de données », ligne `US-221 D1 (PYG) : report de la capture = 55000:leg_movement_unsupported`. Conséquences pour un trip réservé par le vrai checkout : `trip_leg_balance` vide (08 E7 règle 2, 17 §2.9), aucune écriture `COLLECTION` au registre de l'assureur (déclencheur sur `settlement_leg_movement`, 0143), reçu de l'hôte et relevé sans source de capture. Test : « D1 (défaut) » du segment B. Correctif attendu (story argent, revue autre modèle) : rattacher la capture au trip à la conversion et la reporter dans la même transaction, ou ouvrir le report aux opérations du hold converti.
- **D2 — le rapprochement nocturne ne voit pas ce trip** (conséquence de D1) : `core.finance_trip_leg_facts` (0137) ne retient que les trips qui ont un solde par jambe ou un règlement ; un encaissement prouvé jamais porté passe donc sans écart. Test : « D2 (défaut) » du segment B. Correctif : faire partir les faits des encaissements prouvés (`payment_operation` SUCCEEDED du hold converti), pas seulement des soldes.
