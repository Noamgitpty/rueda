# Passation US-104 — Vérification du téléphone par OTP (2026-11-11, agent back-end, claude-opus-5-5)

Branche `story/US-104-otp-telephone`, worktree `../wt/US-104`, PR en brouillon. **Statut : EN REVUE.** Revues exigées (`review-requirements.json`) : code, **sécurité**, **ux**, qa (story) et **architecture** (`packages/db/`), sur un autre modèle que l'auteur. Décision : ADR-098 (PROPOSÉ).

- **Fait** :
  - **Critère 1** (10:00 → 10:11 ⇒ `OTP_EXPIRED` ; 5 codes faux puis un 6e ⇒ `OTP_LOCKED` 1 h) : jugé en base (`0066_iam_phone_otp`) avec les paramètres du pays du défi (`otp_ttl_min`, `otp_max_attempts`, `otp_lock_min`, `otp_sms_fallback_s`, lus en base). Le 5e code faux pose le blocage ; le 6e, même juste, est refusé ; une nouvelle demande aussi, pendant 1 h. Un renvoi ne remet pas les échecs à zéro. Prouvé en L0 (PA, PY, horloge virtuelle) et en contrat HTTP.
  - **Critère 2** (paiement refusé sans numéro vérifié) : `PhoneVerifiedGuard` exporté par IAM (403 `PHONE_NOT_VERIFIED`, état illisible ⇒ refus), testé. **À poser par US-209** sur les routes de paiement, qui n'existent pas encore.
  - **Sécurité** :
    - code tiré par le travailleur `iam_otp_sender` (CSPRNG) ; seule l'empreinte HMAC-SHA-256 sous `RUEDA_OTP_KEY` va en base ;
    - envoi asynchrone (suite N-23 appliquée à l'OTP) : l'événement `iam.otp.requested` ne porte que l'identifiant du défi ;
    - comparaison en temps constant en base ;
    - aucune énumération : même 202 `OTP_SENT`, numéro libre ou pris ; `ACCOUNT_DUPLICATE_PHONE` seulement après le bon code ;
    - plafonds avant toute écriture : numéro, IP, **compte**, **indicatif pays** (nouveaux `otp_rate_*`, graine `0065`), plafond SMS du pays ;
    - purge à 30 jours (`iam_otp_pruner`).
  - **Numéros** : plan de numérotation des mobiles par pays dans `countries.json` (`phone`) ; normalisation E.164, mobiles du pays seulement.
  - **API** : `GET /phone`, `POST /phone/otp`, `POST /phone/verify` (OpenAPI, matrice des routes, `api.md`, `modules.md`). SMS en `FAKE` seulement : le travailleur de production n'a aucun canal SMS (rien ne part).
  - **Écran** `/verify-phone` (étape OTP de S15), en es, en, fr et pt-BR, sans JavaScript, et lien depuis `/login/done` ; catalogue v17 (v15 et v16 prises par US-113 et US-109) ; les 5 clés OTP du prototype US-033 deviennent officielles.
  - **Docs** : ADR-098, README IAM / AUTH / RISK / db, inventaire C0–C4, liste blanche RLS-15, liste blanche pays (0065), ENV_VARS, COMME_TURO (2 lignes), fragment CHANGELOG.

- **Pièges / hypothèses** :
  - IAM ne peut pas dépendre de RISK (RISK dépend d'IAM) : IAM définit le port `OtpSendGuard` et `main.ts` y injecte `risk.guard`. L'intercepteur de RISK pose `Retry-After` sur un `RATE_LIMITED` levé par la route.
  - Groupe `otp_rate_*` et non `rate_limit_*` : 0046 est immuable et son rendu couvre tout le préfixe.
  - Clé absente ⇒ OTP indisponible partout, pas de clé aléatoire par processus : l'API et le travailleur doivent partager la clé.
  - Le lint « constantes pays » prend « Pa » dans « País » : textes `web.s15.phoneCountry` reformulés.
