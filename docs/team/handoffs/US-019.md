## Reprise du 2026-11-03 (revues : code APPROUVÉ ; sécurité, argent, architecture, qa CHANGEMENTS DEMANDÉS)

- Architecture n° 1 et 4 : le travailleur s'appelle `payment_command` (17 §2.3, US-018), et non plus `money_command` ; les politiques de `cmd_money_owner` portent le préfixe `cmd_money_*` (`cmd_money_sel`, `cmd_money_ins`, `cmd_money_upd`) et la famille RLS-15 se nomme `cmd_money`, comme US-018.
- Sécurité n° 7 : les politiques d'écriture de `cmd_money_owner` contrôlent l'acteur `WORKER` et le travailleur : `payment_command` pour l'opération et ses jambes, `payment_command` ou `webhook_ingest` pour les statuts et les événements. Exception déclarée : la boîte de réception et `last_webhook_at` sont écrites par la commande de réception, appelée par `app_api` pour un PSP anonyme.
- Sécurité n° 6, qa n° 7 : `l0-pay-legs-rls.test.ts` porte sur des données réelles, avec le monde d'US-011 et des jambes TJ : le titulaire voit sa seule jambe HOST ; un autre hôte, un co-hôte ou un `org_id` forgé ne voient rien ; FINANCE voit son pays seulement ; ADMIN, selon la portée posée ; OPS, seulement le trip de son dossier ouvert dans son pays (RLS-20) ; SUPPORT sans dossier, le voyageur et une session sans contexte ne voient rien. Les colonnes lisibles excluent `beneficiary_ref`. `trip_id` est maintenant dénormalisé dans `payment_operation_leg` (politique OPS par dossier, comme les règlements en 17 §2.3).
- Argent n° 3, qa n° 8 : le contrôle différé est éprouvé au COMMIT par la fixture `test_fixture.pay_insert_operation_raw` (9500), qui contourne la commande : somme, signe, jambes manquantes ou absentes, VOID avec jambes, jambes sans compte, réaffectation de somme non nulle. Le cas valide est accepté.
- Qa n° 6 : `testing/webhook-http.test.ts` lance une application Nest réelle (`rawBody: true`, port éphémère) : corps signé à espaces non canoniques ⇒ 200 ; corps altéré ou sans signature ⇒ 401 ; doublon ⇒ 200 sans nouvelle ligne ; horodatage hors fenêtre ⇒ QUARANTINED ; registre de production ⇒ 404 sans accès au magasin ; plus de 256 ko ⇒ 413 (la limite JSON d'Express, 100 ko, s'applique avant).
- Fusion de main (US-020) : `packages/fake-adapters` réunit les deux stories (README, package.json, index, lockfile). **Un seul format de rappel signé** : `FAKE_SIGNATURE_HEADER` est exporté une seule fois, par `core/webhook.ts` (fin du TS2308). Les aides restent distinctes : `fakeSignature` / `verifyFakeSignature` (octets bruts, PSP) et `signFakeWebhook` / `checkFakeWebhook` (chaîne, US-020). `CapabilitySet.require` devient `requireCapability`, car le test d'isolement d'US-020 prenait `require(` pour un import dynamique.
- Consigné (mineurs acceptés) :
  - écritures directes héritées de 0007 (`worker_update_status`, `worker_insert_ingest`), à fermer avec US-023 ;
  - garde FAKE à étendre à la préproduction avec US-003 ;
  - la lecture chez le PSP n'est pas rapprochée du montant ni des jambes stockés (story de rapprochement) ;
  - les capacités de montant partiel sont à exiger par l'appelant (US-023, US-024, US-061) ;
  - table `payment_command` (boîte d'envoi, 17 §4.3) non livrée, prévue avec US-023 / US-024.
- **Numérotation** : US-018 a fusionné `0027_settlement_versions_legs` ; la migration de cette story devient `0028_payment_psp_port` (fichier, en-têtes, READMEs, ADR-059, passation, commentaires).
