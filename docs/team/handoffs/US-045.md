## Constats versés aux suites (aucun n'est un défaut du code testé ; rien n'est corrigé ici)

1. **PSP qui ignore l'idempotence** : si notre écriture de statut échoue après un succès du PSP, la commande `PENDING` est rejouée sans lecture préalable (conforme à 17 §4.3 points 2 et 3, qui n'exigent la lecture que pour `UNKNOWN`). Un PSP non idempotent débiterait deux fois ; seul le rapprochement par jambe le détecte (test qui le prouve). Porteurs : porte go / no-go du PSP (idempotence validée en bac à sable) et US-047 ; ou révision de 17 §4.3 (lire avant tout rejeu de `PENDING`).
2. **KYC** : aucun rattrapage par `getStatus` d'un rappel perdu (fail-closed : la personne reste non approuvée jusqu'à la livraison suivante). Une révocation après une approbation appliquée est ignorée (STALE) : aucune spécification ne dit qu'elle doit l'emporter ; question pour la story KYC.
3. **FakePsp** : un `UNREADABLE_AFTER_SUCCESS` scripté sur `LOOKUP` est traité comme un succès de lecture : le cas « lecture illisible » n'est pas simulable (paquet des FAKE).
4. **Webhook tardif dont la lecture échoue** : passe directement à `FAILED SIGNED_TIMESTAMP_UNVERIFIED`, sans nouvel essai dans le processeur ; l'opération attend le rapprochement (fail-closed).
5. **SMS sous `TIMEOUT_AFTER` prolongé** : le message part une fois, puis le repli e-mail part aussi (deux canaux), conformément à `sender.ts`.
6. **Deux régimes de runner** dans l'historique de `main` (p95 autocommit ≈ 80 à 110 ms ou 150 à 250 ms à code proche) : comparer seulement par machine.
