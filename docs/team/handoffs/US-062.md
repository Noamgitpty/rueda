# Passation US-062 — Rôle `P2P_HOST`, politiques RLS de l'hôte, tables d'argent et minimisation (2026-11-03, agent données, claude-opus-5-5)

Branche `story/US-062-role-hote`, worktree `.claude/worktrees/us-062-dev`, PR en brouillon. **Statut : EN REVUE**. Revues exigées :

- code ;
- architecture (`packages/db/`, ADR-064) ;
- **sécurité** (RLS, rôles, `SECURITY DEFINER`, nouveau propriétaire `host_view_owner`) ;
- **argent** (tables d'argent, double validation).

Les revues sécurité et argent se font sur un autre modèle que l'auteur.

- **Fait** :
  - **Critère 1, RLS-2** : le titulaire lit la jambe `HOST` de ses trips seulement, sur les trois tables de jambes. Le co-hôte, l'ancien co-hôte, l'hôte B (même avec l'`org_id` de A) et le titulaire qui réduit sa portée à un véhicule ne lisent rien. Le même particulier, titulaire dans les deux pays, ne voit rien de l'autre pays. Preuve sur des données réelles : règlements v1 enregistrés par `settlement_cmd_record`, montants TJ01 / TJ08a.
  - **Critère 2, RLS-28** : le titulaire donne par erreur `finance.read_org_statements` à son co-hôte. `app.has_permission` est alors vrai, mais `app.is_org_holder()` est faux : le co-hôte lit 0 ligne de jambes, de `host_advance_v` et des tables d'argent.
  - **Critère 3, RLS-21 et RLS-22** :
    - `INSERT`, `UPDATE`, `DELETE` et `TRUNCATE` directs sur les huit tables d'argent sont refusés (`42501`). Les acteurs testés sont, sous `app_api`, le voyageur, l'hôte, OPS et ADMIN ; sous `app_worker`, les travailleurs `settlement`, `payment_command`, `payout` et `bordereau`.
    - `app_worker` n'exécute pas les commandes FINANCE.
    - Après ces tentatives, ADMIN relit des données intactes.
    - `app_anon` n'a aucun droit (`42501`) ; le voyageur et une session sans contexte lisent 0 ligne.
  - **Critère 4, RLS-23 et RLS-25** :
    - OPS sans dossier : 0 ligne ;
    - OPS avec dossier : les jambes du trip du dossier seulement, rien sur `insurer_*`, les avances ni les demandes ;
    - SUPPORT : 0 ligne ;
    - travailleur hors liste blanche (`hold_expiry`, `booking_conversion`, `webhook_ingest`) : 0 ligne, et la commande d'argent est refusée (`42501`).
  - **Critère 5, RLS-24** :
    - FINANCE A et FINANCE B ont la portée `{premier pays}` et ne lisent rien du second pays, même si la portée posée l'inclut.
    - Les actions testées sont `DECIDE_ADVANCE`, `WRITE_OFF_RECEIVABLE` et `ISSUE_BORDEREAU`. Une approbation par A est refusée (`SELF_APPROVAL`), dans la même session, dans une seconde session, et même avec l'`actor_id` de B forgé. Le refus est journalisé et sans effet.
    - L'approbation par B applique l'effet, avec `decided_by` ≠ `decision_second_by`.
    - Une seule demande peut être en attente par action et par sujet.
    - Une demande ou une approbation hors pays rend `FORBIDDEN`, journalisé.
    - L'`UPDATE` direct est refusé (`42501`).
  - **Critère 6, RLS-26 et minimisation** :
    - `core.booking_host_guest_v` rend `trip_id`, prénom, âge, note et statut de vérification, et rien d'autre. Le titulaire voit ses trips ; le co-hôte, les véhicules de sa portée ; l'hôte B, les siens. Le voyageur, le staff et un contexte forgé ne voient rien.
    - `booking_trip.guest_user_id` n'est plus lisible (`42501`). Le voyageur lit toujours ses trips et ses opérations.
    - `core.settlement_host_advance_v` : le titulaire voit sa créance `RELEASED_LEG` seulement, sans identifiant du personnel. Il ne voit ni l'avance d'un autre hôte, ni un crédit `CREDIT_BEYOND_PLATFORM`.
    - `decided_by`, `requested_by` et `issued_by` sont refusés (`42501`). `advance_approvers` ne rend rien à l'hôte et rend les deux personnes à FINANCE.
  - **Reports** :
    - RLS-2 et RLS-21 à RLS-28 d'US-011 : faits, sauf RLS-27 (voir « Reste »).
    - `guest_user_id` de la revue US-011 : fait.
    - Réserves d'US-056 :
      - 3 : politique `cmd_advance_upd`, prouvée par une fixture cédée à `cmd_money_owner` ;
      - 4 : `GRANT` par colonnes existantes ; `trip_id` déjà présent ;
      - 5 : identité par la session du jeton, jamais par `app.*` ;
      - 2 : `cmd_golive_owner` existe déjà ;
      - 1 et la liste blanche de `cmd_golive_owner` : US-125.
  - Migrations `0035_host_permissions_minimization` et `0036_settlement_money_tables_finance`, fixture `9700`, propriétaire `host_view_owner` (amorçage, `OWNER_ROLES`), liste blanche RLS-15 (+5, et `host_covers_vehicle` exécutable par `host_view_owner`). Documentation : ADR-064 et `packages/db/README.md`.

- **Pièges / hypothèses** :
  - **PostgreSQL non démarré en local** : migrations et preuves L0 / int prouvées par la CI seulement.
  - **Nouveau rôle d'instance** `host_view_owner` : un banc natif existant (P-07) doit rejouer l'amorçage.
  - Une politique peut référencer une colonne sans droit de lecture, mais une **sous-requête** de politique, non : d'où la réécriture d'`operation_guest_read`.
  - **Numérotation** : `0035` et `0036` (main à `0034`). US-023 travaille en parallèle sur `packages/db`. Si main avance, renuméroter les fichiers, les en-têtes, le README, ADR-064 et cette passation.
  - Tests adaptés :
    - `l0-rls-columns` : colonnes du trip, tables d'US-062, identifiants du personnel ;
    - `l0-rls-actors` : RLS-12 ;
    - `iam-schema`, `avl-schema`, `audit-schema` : politiques ;
    - `stl-schema` : liste des tables ;
    - `support/rls.ts` : `account` et `staff` exportés.
  - Choix PROPOSÉS (ADR-064) :
    - `has_permission` réservée à `HOST` ;
    - signature à jeton des commandes FINANCE ;
    - issues (`REQUESTED`, `SELF_APPROVAL`, `SUBJECT_CHANGED`…) ;
    - `host_guest_v` réduite aux quatre champs de 19 ;
    - un compte pseudonymisé ne rend ni prénom ni âge.
