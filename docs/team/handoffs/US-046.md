# Passation US-046 — Tests de migrations et de données personnelles (2026-11-04, agent back-end, claude-opus-5-5)

Branche `story/US-046-migrations-donnees-perso`, partie d'`origin/main` (d82a07a), puis `origin/main` fusionné (merge, sans rebase) après la PR #76 (US-004, migration 0051), worktree `.claude/worktrees/us-046-dev`, PR #75 (brouillon). **Statut : EN REVUE.** Revues exigées (`review-requirements.json`) : **code, architecture, sécurité, QA** (story ; `packages/db/`), sur un autre modèle que l'auteur. Rôle d'auteur `back-end`. Décision : ADR-081 (PROPOSÉ). Aucune migration de production, aucun fichier de `.github/`, aucune route, aucune table : `schema.md`, `openapi.json` et la matrice d'US-043 sont inchangés.

- **Fait** (critères de 19 US-046, lus avec ADR-078 : retour arrière sans migration descendante) :
  - **Critère 1, migrations** : `test/l0/l0-us046-migrations.test.ts`, sur une base `_mig` du banc amorcée sans migration, sous `migrator`. Chaque migration de production est appliquée **seule** (option `through` de `runMigrations`), de zéro. Les graines PA / PY (`test/support/migration-seeds.ts`) sont posées dès que leurs tables existent. Après chaque migration, le test vérifie :
    - le schéma de la version N est conservé : relations, colonnes, types, nullabilité, fonctions, droits des rôles applicatifs, sauf dérogation du même fichier ;
    - les comptes et les lignes existantes sont égaux ;
    - aucune contrainte `NOT VALID`, aucune FK orpheline, RLS `ENABLE` + `FORCE` et lecture complète de `migrator` (RLS-19) ;
    - `migrator` voit exactement les lignes posées.

    En fin de parcours : chaîne d'audit valide, second passage vide, migration modifiée, absente, renommée ou rejouée sous un autre numéro refusée. La numérotation contiguë est déjà prouvée par `numbering.test.ts`.

  - **Expand / contract imposé** : lint `sql-expand-contract` (`packages/db/src/expand-contract/`, dans `pnpm lint` et `pnpm lint:sql`), onze natures de contraction, dérogations nominatives dans `packages/db/expand-contract-allowlist.json` (sept entrées historiques justifiées, de 0032 à 0044). Une dérogation périmée échoue aussi.
  - **Critère 2, données personnelles** :
    - inventaire `packages/db/personal-data-inventory.json` : **65 tables, 776 colonnes classées** (C0 à C4), avec classe de suppression, colonnes de sujet, canal d'export et méthode d'effacement de chaque C2 / C3. Complétude contre `schema.md` (unitaire) et contre le catalogue (L0) : une colonne non classée échoue. Les règles et la cohérence avec la matrice d'US-043 sont vérifiées en unitaire ;
    - export `exportOwnPersonalData` (`@rueda/db/privacy`) prouvé en PA et en PY : voyageur et hôte titulaire, exactement leurs lignes, aucune C4, aucune donnée d'autrui, aucune C2 du voyageur chez l'hôte ;
    - destruction de clé pilotée par l'inventaire (`audit_log.ip_enc`, contenu des fichiers) : octets, comptes et chaîne inchangés, sujet illisible, l'autre pays lisible ;
    - aucune donnée personnelle dans les URL, journaux, alertes et erreurs (`apps/api/src/testing/personal-data-leaks.test.ts`) : contrat, analyse statique du code de production, exécution réelle avec une erreur `pg` qui porte l'email dans `detail`.
  - Docs : ADR-081, `packages/db/README.md`, `docs/ops/DEPLOY.md`, `docs/ops/CI.md`.
- **Failles trouvées** :
  1. **0032 n'applique pas sur une base peuplée** : `ADD COLUMN org_id uuid NOT NULL` sans défaut sur les occupations. Écrite pour une table vide, avant toute production ; dérogation `populated: false`, et les graines AVL ne sont posées qu'après elle. 0038 (`SET NOT NULL`) est dans le même cas.
  2. **Motifs C2 dans des registres en ajout seul** : `audit_log.reason`, `data_access_log.purpose`, `finance_approval.reason` (figé par trigger). Ils ne sont ni pseudonymisables ni détruits par la clé du sujet. Dérogations, report à **US-536** : chiffrer par sujet, ou interdire toute donnée de personne dans un motif.
  3. **C2 en clair sans effacement codé** : `iam_session.ip` et `user_agent`, `iam_email_verification.email` et `ip`, `iam_otp_challenge.phone_e164`, `ntf_notification_dispatch.variables`. Méthode déclarée (purge), aucune tâche de rétention ; pseudonymisation des tables B (compte, organisation) non codée. Report **US-536**.
  4. Le contrôle de cohérence a montré qu'`app_api` lit `iam_organization.tax_id`. C'est conforme tant que la colonne reste C2 (annotation de 0010). La classer C3 (n° de pièce, 17 §3.1.4) imposerait de la retirer à `app_api`.
