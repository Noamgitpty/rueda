| 1   | MINEUR  | **La règle « jamais plus que l'encaissé ni que le règlement » est écrite deux fois en SQL sans test d'équivalence.** `payment_assert_settlement_order` (enregistrement : soldes reportés moins en-cours, bornes `[min(0,V) ; max(0,V)]`, Σ ≤ remboursement) et `settlement_cmd_apply_leg_movement` (report, 0116, inchangé) réimplémentent les mêmes bornes avec les mêmes noms de contrainte. Rien ne montre qu'une suite d'ordres acceptée par l'une l'est par l'autre (par exemple un ordre accepté à l'enregistrement puis refusé au report, ou l'inverse). Un test de propriété L0 : pour des suites d'ordres tirées dans les vecteurs (TJ02b, TJ05b, TJ08b, TJ10b), toute suite acceptée à l'enregistrement est applicable au report dans l'ordre, soldes finaux ≤ capture. Les tests actuels contrôlent chaque garde isolément. |
| 2   | MINEUR  | **Aucun test ne relie `settlementOrders` à la garde SQL.** Le calcul pur (TS) et la garde (SQL) sont prouvés chacun contre l'oracle, jamais l'un par l'autre : les L0 construisent leurs ordres avec `negate(vecteur)`, pas avec la sortie de `settlementOrders`. Alimenter la commande par la sortie de la fonction pour TJ05b (réaffectation puis remboursement, dans cet ordre) et TJ16a / b (deux moyens) montrerait que le futur appelant de 224b et la base s'accordent.                                                                                                                                                                                                                                                                                                                                                         |
| 3   | MINEUR  | **`RecordOperationInput` : `kind: string` et `settlement?` optionnel, au lieu d'une union discriminée.** Un REFUND ou une LEG_REALLOCATION sans `settlement` compile et n'échoue qu'en base (`leg_refund_without_settlement`) ; un ordre de capture avec `settlement` compile aussi (refusé par le CHECK). Une union `{ kind: 'REFUND' \| 'LEG_REALLOCATION' \| 'LEG_RELEASE'; settlement: SettlementRef \| null } \| { kind: Autre; settlement?: never }` ferait refuser le mauvais appel à la compilation (le `null` de LEG_RELEASE sans règlement reste exprimable). Le refus en base est le filet ; le typage est gratuit. À faire avec 224b, premier vrai appelant.                                                                                                                                                               |
| 4   | MINEUR  | **`settleOrFinReview(compute: () => T)` ne gère que le synchrone.** Si `T` est une `Promise` (appel asynchrone du moteur ou lecture préalable), le rejet `REFUND_OUT_OF_RANGE` échappe au `try` : ni alerte ni `FIN_REVIEW`, et la fonction rend `SETTLED` avec une promesse qui échouera plus tard. Aujourd'hui `compute` est le moteur pur synchrone ; typer `compute` pour refuser un `Promise` (ou `await` dans le `try`) avant que 224b ne l'appelle.                                                                                                                                                                                                                                                                                                                                                                             |
