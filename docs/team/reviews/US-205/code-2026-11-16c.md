Contexte : qualité, tests contre des attendus indépendants, e2e, double d'API, SQL, seuils visuels.

| #   | Gravité | Constat                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

| 1   | MAJEUR  | **Nouveau SQL du module `cat` jamais exécuté sur une vraie base.** `PgSearchStore.slotCheck` (jointure `LEFT JOIN LATERAL core.catalog_public_terms` et `to_jsonb(t.*)`), `protectionOffered` (`unnest` et `CROSS JOIN LATERAL`) et `termsOf` n'ont aucun test d'intégration : le seul test PG qui construit `PgSearchStore` n'appelle que `listingPrice`, les contrats utilisent le double. Une faute de SQL ou de forme se verrait en production comme un 503 sur la fiche et la recherche. Ajouter un `*.int.test.ts` (PA et PY) : dates acceptées avec conditions (dernière minute et non), `protectionOffered` sur plusieurs annonces. |
| 2   | MINEUR  | **Montants bigint par `to_jsonb`** : sur le chemin `slotCheck`, `extra_km_price_minor`, `deposit_amount_minor` et `rc_amount_minor` traversent un nombre JSON, puis `Number`, puis `String`, alors que `MINOR_TEXT` admet jusqu'à 18 chiffres (au-delà de 2^53 l'arrondi est silencieux). Convertir les bigint en texte dans la requête (`::text`) ou refuser un nombre non sûr ; test avec une valeur supérieure à 2^53.                                                                                                                                                                                                                   |
| 3   | MINEUR  | **Chemin INCLUDED non éprouvé de bout en bout** : `pg-checkout.int.test.ts` ne couvre que l'annonce illimitée ; le gel avec `mileage` INCLUDED produit par `freezeQuote` n'est testé contre la base que par des documents construits à la main (L0). Un écart de forme TS / SQL ne se verrait pas. Ajouter un cas INCLUDED à l'intégration du checkout. La retenue n'y est que bornée (`> 0` et `< total`) : l'attendu exact (oracle) n'est vérifié qu'en unitaire.                                                                                                                                                                         |
| 4   | MINEUR  | **e2e S05** : `toContainText(/0?9/)` est quasi vide de sens (« 9 » suffit) ; viser la date complète localisée de l'oracle (09/12 10:00). Le reste (10:00, 42,80 = 40,00 + 2,80 selon BR-CXL-06 et TA01, 600 km, 0,20) est indépendant du code testé ; projets, `submitAndSettle` et `toHaveTitle` inchangés, pas de sleep ni de retry.                                                                                                                                                                                                                                                                                                      |
| 5   | INFO    | **Tests réels** : `cancellation.test.ts` sur les oracles Python (vecteurs T03, T04, T23, T27, T30, T35, T40, T43, T44, T75, T80 : retenue = total − remboursement) ; `frozen.test.ts` (rejeu identique des devis antérieurs) ; L0 PA / PY sous les rôles de production (200 km × 3 jours = 600, six cas de `QUOTE_MISMATCH`, droits `app_anon` / `app_worker`, fenêtre 90 min puis minimum avec le départ) ; contrat : 429 et `Retry-After`, dernière minute ; `stub-api.mjs` aligné sur l'OpenAPI.                                                                                                                                         |
