# ADR-098 — Vérification du téléphone par OTP : envoi asynchrone sans code en clair, empreinte sous clé hors base, plafonds anti-pumping

- **Statut** : PROPOSÉ (US-104, agent back-end, claude-opus-5-5, 2026-11-11). Revues exigées : code, architecture (`packages/db/`, nouveau travailleur), **sécurité** (`SECURITY DEFINER`, RLS, rôles, clé HMAC, anti-énumération, `packages/db/`), qa, **ux** (« Revue design : OUI » dans 19), sur un autre modèle que l'auteur.
- **Sources** : 19 US-104 (critères d'acceptation) ; 16 VER-013 (« code 6 chiffres … valable 10 min ; 5 essais puis blocage 1 h » ; erreurs `OTP_INVALID`, `OTP_EXPIRED`, `OTP_LOCKED`, `ACCOUNT_DUPLICATE_PHONE` ; « numéro vérifié ailleurs → refus ») ; 08 BR-VERIF-06 ; 17 §3.2.1 (`otp_challenge`, purge 30 j), §4.5 (`iam.phone.verified`), §5 (SMS : « pompage de SMS », « plafonds par numéro et par IP »), §6.6 (OTP, limitation de débit), §7.2 (`otp_ttl_min`, `otp_max_attempts`, `otp_lock_min`, `otp_sms_fallback_s`, « décidé ») ; 10b §4.1 S15, UX-38, W3, §4.3 (`web.s15.codeSent`, `common.error.phoneDigits`) ; ADR-061 (NTF), ADR-075 (anti-abus), ADR-050 (BUS) ; suite **N-23** du BOARD (envoi asynchrone sans jeton en clair à rejouer), appliquée ici à l'OTP.

## Contexte

`core.iam_otp_challenge` existe depuis 0010 sans aucune commande. Le port `MessagingChannel` (SMS) et les plafonds `AbuseGuard` d'US-052 existent, mais aucune route n'envoie d'OTP. La story exige un code tiré d'un CSPRNG et stocké haché, une durée de vie et un nombre d'essais issus des paramètres du pays, une comparaison en temps constant, aucune énumération des numéros, des plafonds contre le SMS pumping (compte, numéro, préfixe pays, IP), une normalisation E.164 en paramètres pays, un envoi asynchrone et un SMS en `FAKE` seulement.

## Décision

1. **Le code naît dans le travailleur, jamais ailleurs.** La demande (`POST /phone/otp` → `core.iam_cmd_phone_otp_request`) écrit un défi **sans code** et l'événement `iam.otp.requested` (identifiant du défi seulement) dans la même transaction. Le travailleur `iam_otp_sender` (consommateur BUS) tire le code (`crypto.randomInt`, 6 chiffres), en dépose l'empreinte (`core.iam_worker_otp_issue`) puis l'envoie par le port `MessagingChannel` (SMS). Le code en clair ne vit que dans la mémoire du travailleur, le temps de l'envoi : ni en base, ni dans l'outbox, ni dans une file, ni dans un journal. Un envoi rejoué après un COMMIT perdu tire un autre code, sous une autre clé d'idempotence (`otp:<défi>:<empreinte courte>`). Aucune nouvelle tentative automatique : la personne redemande après `otp_sms_fallback_s` (16 VER-013).
2. **Empreinte HMAC-SHA-256 sous une clé hors base** (`RUEDA_OTP_KEY`, 32 à 64 octets hex, la même pour l'API et le travailleur). Avec 10^6 codes possibles, un simple condensat serait inversé en une seconde depuis une copie de la base ; la clé l'empêche. Clé absente : **OTP indisponible** (503 `OTP_UNAVAILABLE`, rien n'est émis), dans tous les environnements (une clé aléatoire par processus ne marcherait pas : deux processus). Mal formée : refus de démarrer. Rotation : les codes en cours (10 min au plus) deviennent invalides.
3. **La base juge, avec les paramètres du pays du défi** (lus en base, jamais reçus du client) : durée de vie, essais, blocage, délai de renvoi. Chaque code faux compte ; le `otp_max_attempts`-ième bloque `otp_lock_min` minutes ; pendant le blocage, aucun code (même juste) n'est accepté et aucune nouvelle demande n'aboutit ; les échecs d'un défi vivant se reportent sur le défi suivant (un renvoi ne remet pas le compteur à zéro). Comparaison en **temps constant** en base (`core.iam_otp_hash_equal` : chaque octet lu, écart accumulé, aucune sortie anticipée), sur des empreintes de 32 octets. Expiré : `OTP_EXPIRED`, sans essai compté.
4. **Aucune énumération.** La demande rend `OTP_SENT` (202), avec le même corps, que le numéro soit libre ou déjà vérifié par un autre compte. `ACCOUNT_DUPLICATE_PHONE` (16 VER-013) n'est rendu qu'après la saisie du **code juste**, donc à qui possède le numéro. Un numéro vérifié n'appartient qu'à un compte (index unique de 0010, verrou consultatif par numéro).
5. **Plafonds anti-pumping avant toute écriture** (`AbuseGuard.checkCostlySend` de RISK, injecté dans IAM par la racine de composition, car RISK dépend déjà d'IAM) : par numéro et par IP (US-052), **par compte** et **par indicatif pays** (nouveaux paramètres `otp_rate_per_account_hour`, `otp_rate_per_prefix_hour`, graine 0065), puis plafond SMS journalier du pays. Refus : 429 `RATE_LIMITED` avec `Retry-After` (ou 503 si le compteur manque), aucun défi. Un renvoi demandé avant le délai rend la même réponse sans rien consommer. Groupe `otp_rate_*` et non `rate_limit_*` : 0046 est immuable (ADR-044) et son rendu couvre tout le préfixe `rate_limit_`.
6. **Numéro normalisé en E.164 d'après le plan du pays** (`countries.json`, champ `phone` : indicatif, longueur du numéro national d'un mobile, premiers chiffres des mobiles, préfixe interurbain, exemple affiché). Seuls les **mobiles du pays choisi** sont admis (parade au pumping vers des lignes fixes, surtaxées ou étrangères ; PROPOSÉ). La base ne vérifie que la forme E.164 générique.
7. **Contrôle bloquant du paiement** : `PhoneVerifiedGuard` (exporté par IAM ; 403 `PHONE_NOT_VERIFIED`, état illisible ⇒ refus) à poser par US-209 sur les routes de paiement.
8. **Purge à 30 jours** (17 §3.2.1) par le travailleur périodique `iam_otp_pruner` ; la politique de suppression borne elle-même à 30 jours.
9. **SMS en `FAKE` seulement** : le travailleur de production n'a aucun canal SMS avant le lot C (F-03) : rien n'est envoyé (journal `NOT_SENT`, `CHANNEL_MISSING`). WhatsApp (lot 5) et le repli e-mail ne s'appliquent pas à la vérification d'un **numéro** : un code par e-mail ne prouve pas la possession du téléphone (PROPOSÉ, comme Turo : SMS).

## Conséquences

- Tant qu'aucun canal SMS réel n'existe (lot C), la production ne vérifie aucun numéro : le paiement, quand US-209 posera le contrôle bloquant, restera fermé. C'est le défaut fail-closed voulu.
- `RUEDA_OTP_KEY` devra être créée au coffre (et dans l'IaC : `secrets.tf`, `compose.yaml`) avec le canal SMS réel ; sans elle, l'OTP reste indisponible.
- Détection du type de ligne (VoIP, 16 VER-013) : sans fournisseur, `phone_line_type` reste NULL (« type inconnu → accepté et signalé à ADM-029 », signalement à faire avec ADM-029) ; l'événement porte `line_type: null`.
- Un attaquant peut bloquer pendant une heure l'OTP de **son propre** compte seulement : le blocage est par compte, pas par numéro (un tiers ne peut pas bloquer le numéro d'autrui).
