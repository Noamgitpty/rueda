# ADR-067 — Socle de marque modifiable : thème versionné en base, publication atomique, contenus trilingues

- **Statut** : PROPOSÉ (US-034, agent back-end, 2026-11-03). Revues exigées : code, **architecture** (`packages/db/`, nouveau sous-domaine CFG) et **sécurité** (RLS, `SECURITY DEFINER`, permission `brand.publish`, fichiers publics), sur un autre modèle que l'auteur. À reporter dans 17 §8.1.
- **Stories** : US-034 ; s'appuient dessus US-120 (écran « Apparence / Marque »), US-121 (blocs de contenu dans le site), US-126 (manifeste PWA), US-020 (habillage des e-mails), US-538 (WhatsApp, lot 5), US-003 (stockage objet réel). **Sources** : DEC-FONDATEUR-07, DEC-MARQUE ; 04 DSN-002, DSN-004 ; 16 DSN-001 à DSN-004 ; 17 §1.7, §3.2.13, ADR-036 ; ADR-047 (jetons, contrôle de contraste), ADR-051 (chaîne d'audit, `file_asset`), ADR-056 (forme d'appel), ADR-062 (commandes de console).

## Contexte

Le fondateur veut pouvoir changer le design à tout moment : retouche, retour à une ancienne palette ou design neuf, sans déploiement (DEC-FONDATEUR-07). US-030 a fait des jetons la source unique du thème, mais lus dans des fichiers compilés : changer de palette demande un redémarrage ou une reconstruction. 17 §3.2.13 prévoit `brand_version`, `brand_asset` et `content_block` (module CFG). 19 US-034 exige une publication atomique, un retour arrière en un clic journalisé, le refus d'une police hors liste (`FONT_NOT_APPROVED`) et le refus d'une version dont une paire échoue au contraste AA, avec **le même contrôle qu'US-030**, avant même l'écran US-120.

## Décision

1. **Tables** (migration `0042_config_brand`, schéma Bêta `core`, préfixe `config_` du module CFG) : `config_brand_version`, `config_brand_asset`, `config_content_block`, conformes à 17 §3.2.13. Écarts PROPOSÉS, à reporter dans 17 :
   - `brand_version.request_id` (idempotence), `archived_at`, `created_at` ;
   - `brand_asset` : `alt_text_fr` (trilingue, US-060) ; copie figée de `storage_key`, `mime`, `bytes`, `sha256` du `file_asset` (la lecture publique ne touche jamais une table d'audit) ; `request_id` ; `created_at` ;
   - `content_block` : `request_id`, `archived_at` ; `country_code char(2)` (clé étrangère vers `config_country`).
2. **Le thème est un document DTCG complet** (`tokens`), au format des palettes US-028 : une retouche, une ancienne palette (`fromPalette`, copie du registre) et un design entièrement neuf passent par le même chemin. Aucune couleur ni police dans le code ; `tokens_schema_version` = `TOKENS_SCHEMA_VERSION` d'US-030.
3. **Versions jamais écrasées** (gardes, tous rôles, `migrator` compris) : un brouillon est immuable (modifier = nouveau brouillon) ; seules transitions : `DRAFT → PUBLISHED`, `PUBLISHED → ARCHIVED` ; aucun `DELETE`, aucun `TRUNCATE` ; un actif est immuable.
4. **Écriture uniquement par commandes** `SECURITY DEFINER`, propriétaire NOLOGIN **`iam_staff_owner`**, EXECUTE au seul `app_api`, liste blanche RLS-15 (8 entrées) : `cfg_brand_cmd_register_asset`, `cfg_brand_cmd_save_draft`, `cfg_brand_cmd_publish`, `cfg_brand_cmd_rollback`, `cfg_brand_staff_versions`, `cfg_content_cmd_save_draft`, `cfg_content_cmd_publish`, `cfg_content_cmd_rollback`. Chaque commande suit ADR-062 : session retrouvée par l'empreinte du jeton, TOTP exigé, permission relue dans `iam_role_permission`, refus **journalisé** (`STAFF_ACCESS_DENIED`, `STAFF_FORBIDDEN`), audit écrit **en dernier** (`core.iam_staff_audit`, chaîne d'US-009). Forme d'appel d'ADR-056 : un appel = une instruction, en autocommit.
   - **Pourquoi `iam_staff_owner`** : ce sont des commandes de console (ADR-062 : « chaque commande de console est un appel SECURITY DEFINER sous `iam_staff_owner` »), qui réutilisent ses aides (`iam_staff_session`, `iam_staff_permitted`, `iam_staff_audit`) et ses droits de lecture sur la session et la matrice. Un propriétaire dédié (`cfg_brand_owner`) aurait dupliqué ces droits sur cinq tables IAM et sur le journal ; il reste possible si la revue sécurité le préfère (amorçage, `OWNER_ROLES`, liste blanche). Droits ajoutés à `iam_staff_owner` : lecture et écriture **par colonnes** des trois tables (politiques `iam_staff_*`), et `INSERT` sur `audit_file_asset` borné par la politique à `bucket = 'BRAND'`, `C0`, `STAFF_UPLOAD`, sans clé de sujet.
5. **Permissions** (semées, 17 §3.2.13 et 16 DSN-003) : `brand.edit` (brouillons, actifs, historique) et `brand.publish` (publication, retour arrière), rôle `ADMIN` seulement. **Portée** : le thème est commun (16 DSN-002 SIMPLIFIÉ) ; il faut donc la permission sur **tous** les pays déclarés (`config_country`, aucune constante). Un bloc de contenu d'un pays demande la permission sur ce pays ; un bloc commun, sur tous. PROPOSÉ, fail-closed.
6. **Publication atomique** : sous un verrou consultatif de transaction (`hashtextextended('core.config_brand_version', 0)`), dans la même instruction, l'ancienne version passe `ARCHIVED` puis le brouillon `PUBLISHED` ; l'index unique partiel `brand_version_one_published` garantit une seule version publiée ; la numérotation (`max + 1`) se fait sous le même verrou. Blocs : verrou par (clé, pays), index unique partiel `(block_key, locale, country_code) NULLS NOT DISTINCT WHERE status = 'PUBLISHED'`. Preuve : 8 publications concurrentes, toutes sérialisées, une seule version publiée à la fin (`l0-brand`).
7. **Retour arrière** = **nouvelle version** copiée d'une version `ARCHIVED` (`copied_from_id`), publiée dans la même instruction (17 §3.2.13 : jamais d'écrasement). « Un clic » : l'API choisit par défaut la version publiée avant l'actuelle (la plus récemment archivée) ; un bloc de contenu retombe de même sur sa dernière version archivée.
8. **Contraste : le contrôle d'US-030, réutilisé, jamais recopié.** L'API construit le thème (`buildTheme`) et appelle `checkContrast` de `@rueda/design-tokens` (mêmes `CONTRAST_RULES`, même verre au pire cas) sur les jetons **du brouillon relu en base** (immuable, donc sans écart entre contrôle et publication). Le rapport (`checker`, `passed`, `failures` avec mode, paire, ratio, seuil) est passé à la commande :
   - échec : la commande **journalise** le refus (`BRAND_PUBLISH_REFUSED` / `BRAND_ROLLBACK_REFUSED`, paires en cause dans `after.failures`), ne change rien, et l'API répond `BRAND_CONTRAST_INSUFFICIENT` en nommant chaque paire ;
   - défense en profondeur : une contrainte `CHECK` refuse toute version non brouillon dont `contrast_check` n'est pas « `passed` = true, `failures` = [], `checker` nommé » ; un rapport forgé « passé » avec une paire en échec est refusé comme un échec.
   - **Limite assumée** : la base ne recalcule pas le contraste (pas de recopie de l'algorithme en SQL, consigne de la story). Elle fait confiance au rapport d'`app_api`, mais seul un ADMIN élevé par TOTP peut publier, et chaque publication est journalisée avec son rapport. Un retour arrière repasse le contrôle **actuel** (il a pu se durcir depuis).
9. **Polices approuvées** : un paramètre de plateforme, `apps/api/src/modules/cfg/data/brand.json` (`approvedFonts`, avec la licence de chaque police), validé fail-closed au démarrage (`CONFIG_INVALID`). Il contient au départ toutes les polices des palettes US-028, pour qu'un retour à n'importe quelle palette reste possible (un test le vérifie). `themeFontFamilies` (ajouté à `@rueda/design-tokens`) liste les familles nommées ; les familles génériques ne sont pas à approuver. Police hors liste : `FONT_NOT_APPROVED` dès l'enregistrement du brouillon, et de nouveau à la publication. Hors du registre pays de 17 §7.2, parce que le thème est commun aux deux pays ; ajouter une police = vérifier sa licence et ouvrir une demande de fusion (PROPOSÉ ; US-120 pourra la porter en base).
10. **Fichiers** : l'API vérifie le type **réel** des octets (signatures PNG, JPEG, WebP, WOFF2), refuse le SVG (script possible dans un bucket public), calcule le SHA-256, puis la commande écrit `file_asset` (bucket `BRAND`, `C0`, `STAFF_UPLOAD`, rétention `BRAND_PUBLIC`) et `brand_asset` **avant** le dépôt de l'objet (ordre de la revue US-009, port en création seule). Stockage : port `BrandFileStore`, structurellement compatible avec `InMemoryFileStore` (FAKE, tests) ; en production, `UnavailableBrandFileStore` tant qu'US-003 n'a pas livré le stockage objet. Un actif n'est lisible publiquement que s'il est référencé par une version ou un bloc publiés. Les actifs sont servis avec `nosniff`, `Content-Security-Policy: default-src 'none'` et un cache long (immuables).
11. **Lecture publique mise en cache** : `GET /brand` (jetons, feuille de style prête issue de `themeStyleSheet`, actifs, ETag par version, 304), `GET /brand/content?locale&country` (bloc du pays prioritaire sur le bloc commun, repli `es` signalé par `fallback`), `GET /brand/assets/:id`. `app_api` ne lit que les lignes `PUBLISHED`, sans colonne d'auteur ni de requête. Cache en mémoire **vidé à chaque publication ou retour arrière** de l'instance qui publie, et borné ailleurs par `readCacheTtlSeconds` (30 s PROPOSÉ, plafonné à 60 s : 16 DSN-003 « moins d'une minute »). Aucune version publiée : `503 BRAND_VERSION_UNAVAILABLE`, le client garde son thème embarqué (US-030).
12. **Trilingue** : un brouillon de bloc crée **les trois langues** (es, en, fr) sous le même numéro ; une langue absente ou vide est refusée (`CONTENT_BLOCK_REQUIRED_MISSING`) ; la publication et le retour arrière portent sur les trois ensemble. Les textes alternatifs des images sont exigés dans les trois langues. Clés `legal.*` refusées (17 §3.2.13). Markdown restreint, contrôlé par l'API et par une contrainte de la base : aucune balise HTML, aucune URL absolue, liens internes (`/…`, `#…`) seulement, aucun lien par référence.

## Conséquences

- Le fondateur peut, dès US-120, retoucher la palette, revenir à une palette d'US-028 ou publier un design neuf ; chaque publication et chaque retour arrière sont dans la chaîne d'audit, avec l'auteur et le rapport de contraste.
- Le contrôle de contraste reste unique (`@rueda/design-tokens`) : le durcir change à la fois le chargement d'une palette (US-030) et la publication (US-034).
- `@rueda/design-tokens` devient une dépendance d'exécution de l'API (source TypeScript, chargée par Node 26 sans étape de construction ; les palettes `docs/design/US-028/` doivent donc être présentes dans l'image, à prévoir par US-003).
- `iam_staff_owner` gagne des droits d'écriture sur les tables de marque et l'insertion de `file_asset` du bucket BRAND.
- **Reste** : brancher le site (`apps/web/theme.tsx`) et le back-office sur `GET /brand` avec repli sur le thème embarqué (US-120 ou US-032) ; invalidation entre instances par événement (`config.brand.published`, outbox) si le délai du cache devient gênant ; habillage des e-mails (`email_skin`, US-020) ; surcharges par pays (P1).

## Solutions écartées

- **Recopier le contrôle de contraste en PL/pgSQL** : deux implémentations divergeraient ; consigne explicite de la story.
- **Stocker seulement un identifiant de palette et des surcharges** : un design neuf exigerait un déploiement (nouvelle palette au registre).
- **Modifier un brouillon en place** : obligerait à lier le rapport de contraste à un état précis des jetons (empreinte) ; l'immuabilité supprime ce risque.
- **Paramètre dans le registre pays (17 §7.2)** : la migration de graines 0009 est générée et déjà appliquée ; un paramètre commun aux deux pays n'y a pas sa place en Bêta.

## Si abandonné

Thème en fichiers de configuration versionnés (US-030, ADR-047) : mêmes jetons, changement par déploiement (repli prévu par ADR-036).
