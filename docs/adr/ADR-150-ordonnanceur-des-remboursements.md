# ADR-150 — Ordonnanceur des remboursements planifiés et états SM-8 après l'envoi

- **Statut** : PROPOSÉ (US-224, partie 224c, agent argent / back-end, claude-opus-5-5, 2026-11-17). Revues exigées (`check-story-reviews.mjs`) : argent et sécurité (`SECURITY DEFINER`, RLS, rôles, concurrence) sur un autre modèle que l'auteur, puis celles que le script ajoute. À reporter dans 17 §3.2.7 (`refund_instance.fin_alert`), §4.3 (ordonnanceur, verrous pendant l'appel au PSP), §2.3 (travailleur `refund_scheduler`) ; alertes en 17 §6.
- **Complète** ADR-147 (instance `PLANNED` / `SUBMITTED` / `SUPERSEDED`, avance de Kmino, envoi autorisé) et ADR-148 (annulations réglées : le remboursement naît `PLANNED`, sans ordonnanceur jusqu'ici).
- **Sources** : 19 US-224 (critères 1 et 4) ; 08 SM-8, E4, BR-PAY-08 ; 17 v6 §2.8 (port, lecture d'abord, capacité inconnue = non), §4.3 points 1 à 4 ; BOARD N-225 (périmètre de 224c), N-227 ; revues de la PR #202 (sécurité n° 3 : verrou de l'ordre pendant l'appel, relecture du statut et de la version en tête ; sécurité n° 1 : matrice).

## Contexte

Depuis 224b, un remboursement est une instance `PLANNED` avec son ordre `REFUND` PENDING ; depuis 215a, chaque annulation de l'ops en crée une. Rien ne les envoie : aucun service n'autorise l'envoi, n'appelle le PSP, ne suit l'ordre après `SUBMITTED` ni ne reporte le remboursement prouvé. `MoneyCommandSender` (US-061) appelle le PSP avant d'écrire le statut : sans verrou tenu pendant l'appel, deux travailleurs pourraient envoyer le même ordre.

## Décision

1. **Tâche périodique `refund_scheduler`** (STL, `RefundScheduler`, 10 s, 50 instances par passage, PROPOSÉ comme la conversion et les annulations) : file `core.payment_refunds_due` (instances `PLANNED`, non bloquées d'abord ; `SUBMITTED` / `SENT` dont l'ordre attend le PSP ; `CONFIRMED` prouvées non reportées ; `FAILED` non signalées). **Une transaction par instance** sous le nom `payment_command` (celui qu'exigent les commandes d'argent) ; une instance ne bloque jamais les suivantes (`process` ne lève pas).
2. **Connecteur par fournisseur** (`PaymentConnectorRegistry` de PAY) : sans connecteur pour le fournisseur de l'ordre, **rien n'est autorisé ni envoyé** (une instance `SUBMITTED` ne peut plus être remplacée, 08 SM-8 : on ne l'autorise pas sans pouvoir l'envoyer). Production : registre vide jusqu'au lot C (`PRODUCTION_PAYMENT_CONNECTORS`, aucune option pour en injecter un autre, comme les webhooks, C19). Le FAKE n'est fourni qu'aux tests.
3. **Envoi autorisé puis appel au PSP dans la même transaction** : `core.payment_cmd_submit_refund` (verrou du trip, avance décidée, date d'émission), puis `core.payment_cmd_refund_order_for_send` qui prend le verrou du trip PUIS celui de l'ordre (`FOR UPDATE`), **gardés jusqu'au COMMIT, donc pendant l'appel au PSP**, relit l'instance, l'ordre et la version en tête, et rend l'ordre STOCKÉ (clé `idem_sent`, montant, jambes de `payment_operation_leg`, référence PSP de l'encaissement remboursé). Aucun montant n'est calculé : `MoneyCommandSender` envoie le montant explicite de chaque jambe (jamais un prorata), lit d'abord si l'issue est inconnue ou si l'en-tête d'idempotence n'est pas validé, et écrit le statut par `core.payment_cmd_apply_operation_status`.
   3 bis. **Jamais `SUBMITTED` sans envoi** (revues de la PR #207) : l'envoi autorisé n'est validé que si l'ordre a atteint le PSP (réponse, refus reçu, issue inconnue). PSP injoignable (`NOT_SENT`), aucune lecture possible (`ESCALATE`) ou ordre non envoyable relu après l'autorisation : la transaction est **annulée**, l'instance reste `PLANNED` sans date d'émission et reste remplaçable. La référence PSP de l'encaissement est lue **avant** l'envoi autorisé (`target_known` de la file) : sans elle, rien n'est autorisé (`NO_TARGET`, revue FIN). Sans connecteur, aucune transaction n'est ouverte.
4. **Ordre jamais envoyé d'une version remplacée** (`SUPERSEDED_UNSENT`) : l'instance `SUBMITTED` reste engagée (08 SM-8) mais l'ordre ne part pas sans revue FIN (la version n+1 recalcule ce qui reste à rembourser). `NO_TARGET` (encaissement sans référence PSP) : revue FIN.
5. **SM-8 après l'envoi** (migration 0127) : déclencheur `refund_instance_sync` (`SECURITY DEFINER` sous `cmd_money_owner`) sur le statut de l'ordre `REFUND` : `SUBMITTED` ⇒ instance `SENT` ; `SUCCEEDED` ⇒ `SENT` puis `CONFIRMED` (jamais de saut) ; `FAILED` ⇒ `FAILED` ; `UNKNOWN` ⇒ inchangée (« un remboursement SUBMITTED sans réponse reste SUBMITTED »). Écrivains : `payment_command` (réponse ou lecture du PSP, politique existante) et `webhook_ingest` (preuve signée, politique `cmd_money_sync` limitée à `SUBMITTED` / `SENT` → `SENT` / `CONFIRMED` / `FAILED`). La garde de l'instance admet `SUBMITTED → SENT | FAILED`, `SENT → CONFIRMED | FAILED`, `FAILED → SUPERSEDED` ; la supersession (version n+1) remplace aussi les instances `FAILED` et annule leur avance attendue ; une instance remplacée après un échec garde sa date d'émission (CHECK élargi).
6. **Report** : une instance `CONFIRMED` dont l'ordre porte une preuve (webhook signé, ou lecture d'un compte de bac à sable hors production) est reportée sur les soldes des jambes (`core.settlement_cmd_apply_leg_movement`, l'avance décidée devient `OPEN`). Sans preuve, elle attend hors de la file.
7. **Alertes FIN, une fois par état** : `FIN_REFUND_BLOCKED` (P1, avance sans décision FINANCE : motif `ADVANCE_CAP_UNSET`, `HOST_ADVANCE_CAP`, `PLATFORM_BALANCE_UNKNOWN` ; critère 4) ; `FIN_REFUND_FAILED` (P1 : échec du PSP, escalade sans lecture possible, `MISMATCH`, envoi refusé, refus de la base nommé par sa contrainte, erreur inattendue). Étiquettes : pays et code seulement. La clé de l'état signalé est posée dans `refund_instance.fin_alert` (`core.payment_cmd_refund_mark_alerted`) APRÈS l'envoi de l'alerte : une alerte perdue est rejouée au passage suivant, jamais deux fois le même état.
8. **Matrice d'autorisations** : `payment_refund_instance` est peuplée dans le monde de la matrice (fixture 9961 : une instance par trip encaissé, règlement en tête) ; l'exception `sans_donnees` est retirée : chaque cellule de lecture (FINANCE / ADMIN du pays, travailleurs d'argent, refus de tout autre acteur) est éprouvée sur des lignes réelles.

9. **File sans famine** : les instances déjà signalées (`fin_alert` posé : bloquées, escaladées, report refusé) passent après les autres, puis les bloquées ; un lot de 50 instances coincées n'affame jamais les suivantes.

## Écart assumé avec 17 §4.2 (effet externe dans une transaction rejouable)

17 §4.2 (VERIF_17-A5) veut qu'aucune transaction rejouable ne contienne d'effet externe. Ici l'appel au PSP est fait DANS la transaction qui tient les verrous : si elle prend `40P01` / `40001` (ou si le COMMIT échoue) après l'appel, le statut écrit est perdu et l'ordre est relu ou renvoyé au passage suivant. C'est sûr par construction : clé d'idempotence STOCKÉE (`idem_sent`) renvoyée à l'identique, lecture d'abord sans en-tête d'idempotence validé ou après une issue inconnue, escalade sans lecture possible (17 §2.8, N-108). Conditions bloquantes avant le lot C (GL-30) : **délai d'appel borné imposé par l'ordonnanceur** (les verrous du trip et de l'ordre sont tenus pendant l'appel ; aujourd'hui le délai est celui de l'adaptateur) ; **rétention de la clé d'idempotence chez le PSP** supérieure à la plus longue reprise possible (une reprise après un long arrêt ne doit jamais renvoyer une clé oubliée) ; escalade d'un remboursement `SENT` sans preuve depuis trop longtemps (`ops_monitor` ne surveille que `UNKNOWN`).

## Alternatives écartées

- **Autoriser l'envoi sans connecteur** (production avant le lot C) : l'instance passerait `SUBMITTED`, donc non remplaçable et datée, sans jamais partir. Refusé (fail-closed).
- **Appel au PSP hors transaction** (envoi autorisé validé, puis appel, puis statut) : deux travailleurs pourraient envoyer le même ordre entre la relecture et l'écriture du statut (revue sécurité de #202, n° 3). Retenu : verrous tenus pendant l'appel ; le PSP lent retient le trip, borné par le délai de l'adaptateur (lot C).
- **États SM-8 écrits par l'ordonnanceur** : la preuve signée arrive par `webhook_ingest`, pas par l'ordonnanceur ; un déclencheur sur le statut de l'ordre suit tous les écrivains autorisés.
- **Alerte à chaque passage** (10 s) : bruit ; une colonne de la dernière alerte par instance suffit.

## Limites et conséquences

- **Ordre des verrous de la marque de l'alerte** (US-224, durcissement argent n° 2, migration 0151, BOARD N-364) : `core.payment_cmd_refund_mark_alerted` prend le verrou du trip puis la ligne de l'instance, comme l'envoi et le report ; l'ordonnanceur attend le choix du rail avant de marquer (ADR-166 décision 7). Aucun interblocage avec la supersession, prouvé à deux connexions (`l0-us224-await-choice-race`).

- **Nouvelle tentative après `FAILED`** et choix du rail (`PENDING_CUSTOMER_CHOICE`, `attempt_no` + 1) : non construits ; un échec est signalé à FIN, l'avance attendue reste `PLANNED` (aucune créance) jusqu'à la version suivante. Suite.
- **Instance exigée pour tout `REFUND` de règlement** (revues de #202) : non rendue obligatoire en base ici ; le seul chemin de production (annulations de 215a, ordonnanceur) passe par l'instance. La garde exigerait de réécrire une soixantaine d'appels des preuves de sécurité de 224a (`l0-us224-*`, `l0-us049`, `l0-pay-marketplace`, `redteam-argent-psp-legs`) : suite à part, revue sécurité.
- **File ops `MISMATCH`** (N-196) : un `MISMATCH` rendu au webhook (`webhook_ingest`) n'est pas encore mis en file ; l'ordonnanceur ne le voit qu'à la lecture (alerte). File FIN persistante de `REFUND_OUT_OF_RANGE` (N-13 a) : inchangée (alerte de 224a).
- Écran S10 et lecture du remboursement (critère 1, UXQ-11), hôte défaillant (critère 5), remboursement multi-moyens (TJ16), GL-21 en base (N-226) : suites.
- Un écrivain du statut d'un ordre `REFUND` autre que `payment_command` et `webhook_ingest` (aucun aujourd'hui ; `app_worker` ne peut écrire qu'un statut non terminal pour d'autres travailleurs) ne ferait pas suivre l'instance (mise à jour sans effet sous la RLS) : l'instance resterait `SUBMITTED`, en file, relue au PSP.
- « Ordre `PENDING` = jamais envoyé » (`SUPERSEDED_UNSENT`) est une hypothèse : une réponse `SUCCEEDED` non prouvée (`AWAITING_PROOF`, compte LIVE) laisse l'ordre `PENDING` alors que le PSP a agi. Le blocage reste prudent (aucun renvoi, revue FIN) ; le libellé exact est « aucun statut du PSP prouvé ».
- Un refus déterministe du PSP (`IDEMPOTENCY_CONFLICT`, `INVALID_REQUEST`) ou un report refusé est rejoué à chaque passage (après les autres instances, alerte unique) : recul exponentiel par instance en suite.
- La lecture d'un ordre en vol a lieu à chaque passage (10 s) : à espacer selon les limites du PSP réel (lot C).
- Verrou de l'ordre pendant l'appel : prouvé par la structure (une transaction, `FOR UPDATE` dans la commande, test unitaire : envoi autorisé, relecture et appel dans la même transaction) ; une preuve à deux connexions exige des données validées (suite QA, fichier isolé).
